Appendix D — Upcoming Changes and Improvements

{#sec-upcoming-changes}

This appendix records proposed changes and improvements to the governance framework and its companion documents that are under consideration but have not yet been incorporated. Items are captured here to maintain a visible development log between formal review cycles.

It also serves as a record of substantive review findings, including external assessments, that have shaped or are expected to shape future versions of the suite.

D.1 Review: Framework Effectiveness Assessment (March 2026)

The following section records a structured review of the document suite against the question: In terms of a data and digital asset governance document, is it effective? Where is it weak?

Reviewer: Claude (AI assistant), prompted by Jonathan Payne, 22 March 2026

D.1.1 Where the Suite is Effective

It addresses its stated problem. The problem statement identifies five concrete risks: no version records, no owners, no audit trail, knowledge loss on turnover, compliance risk. The framework addresses all five with specific, actionable mechanisms. It reads as a document written by someone who has lived with the consequences of not having it.

The tier system is the right design choice. A single governance weight applied to all assets would either over-govern experiments or under-govern operational assets. The three-tier model is proportionate and gives teams permission to be light-touch where it matters less, making them more likely to be rigorous where it matters most.

The hydrometric data chapter is strong. Bronze/Silver/Gold with immutable Bronze, explicit approval gates at each transition, named roles per tier, quarterly reporting, and the principle that data is never overwritten in place. This is well-implemented data governance for a small operational team. The Q-FAIR alignment is embedded structurally, not added as a compliance overlay.

The alignment register is unusually mature. Most team-level governance documents do not trace their requirements back to external policy. This suite identifies nine specific divergences against CDDO, Defra, Cabinet Office, and the National Data Strategy, resolves eight, and documents the justification for the one intentional deviation. That is a strong audit position.

The model condition framework is original and practical. Five-factor scoring (0–10) with defined required actions at each threshold band, including mandatory suspension at Critical, goes beyond what most modelling teams have. The distinction between condition and performance (that a model may still produce acceptable outputs while being in poor condition) is important and well-articulated.

D.1.2 Where the Suite is Weak

The following weaknesses were identified. Each is provisionally assigned a priority for resolution.

D.1.2.1 1. No Implementation Authority

Partially resolved at v1.4

Implementation dates have been set and are now recorded in the parent framework metadata block:

  • Implementation start: 23 March 2026
  • Target adoption: 31 March 2026 (end of financial year 2025-26)
  • Review date: 31 March 2027

All companion document review dates have been updated to reflect the same review cycle.

What still remains: Owner signatures on the approval blocks, and the transition period and register population targets described below. These require Owner engagement and cannot be set unilaterally.

The suite is Draft: For Review. Approval blocks are unsigned and there is no statement of what happens between now and formal adoption. A governance framework without an approval date is a set of suggestions.

What is needed: Owner signatures on the approval blocks, and a transition period for compliance with target dates for populating each register with real asset entries.

Priority: High. Resolves before or at the point of adoption.

D.1.2.2 2. Heavy on “What”, Light on “How”

Partially resolved at v1.4 — Hydrometric Data Register and Tool Register

Hydrometric Data Register: A CSV file maintained by the reach.io R package (github.com/JonPayneEA/reach.io) via write_provenance_record(). A separate Gauge Registry (Parquet) is managed by build_gauge_registry(). Chapter 5 updated.

Tool Register: A generated CSV (tool_register.csv) produced by scripts/build_tool_register.R. The script queries the GitHub API for all repositories in the JonPayneEA organisation and merges each repository’s governance.yml with GitHub metadata. It is not hand-maintained. A governance-template.yml is provided for tool repositories to adopt. The parent framework (Section 7.6) has been updated to reflect this.

The framework defines excellent structures (registers, run records, condition assessments, provenance records) but rarely explains how to create or maintain them in practice. There are no templates, no worked examples, and no indication of where registers live or what format they take.

Specifically: - The Hydrometric Data Register format is now resolved via reach.io (see note above). - The Tool Register format is now resolved via scripts/build_tool_register.R (see note above). - The Model Register physical form is still undefined. - Run records have a 13-field template but no completed example. - The data catalogue is required but its format is left open (“a structured document, a spreadsheet, or a dedicated section”), which in practice means it does not yet exist.

What is needed: Decisions on the Model Register format, a completed run record example, and a data catalogue format decision.

Priority: High.

D.1.2.3 3. Governance Load Not Matched to Capacity

Partially resolved at v1.4

A phased compliance timeline has been added to the new Implementation chapter (Chapter 8, Chapter 8). Phase 1 obligations apply from 1 April 2026 and cover registration and role confirmation only. Full framework obligations, including quarterly summaries, condition assessments, and the annual audit, apply from 1 April 2027. The fw-governance MCP server (Appendix F, Appendix F) automates the mechanical portions of the monitoring obligations once registers are in place. Outstanding: the timeline requires Owner agreement before the effective date.

The framework creates a significant and recurring administrative burden:

  • Quarterly governance summaries from the Steward
  • Annual Tier 1 audit across all tools, models, and data
  • Annual condition assessments for all Tier 1 models
  • Six-monthly access reviews
  • Monthly Data Quality Issue Log reviews
  • Annual framework review with Owner sign-off
  • Annual training verification

For a team where, by the problem statement’s own admission, models currently lack version records and tools lack owners, this is a large step change with no phasing. The risk is that the framework is adopted on paper but not in practice because no one has capacity to run all the review cycles. The fw-governance MCP server (Appendix F, Appendix F) directly addresses this by automating the mechanical portions of many of these obligations.

What is needed: Either a phased compliance timeline that ramps obligations up over 12–18 months as registers are populated and tooling is in place, or explicit acknowledgement that certain obligations (e.g. quarterly summaries, formal condition assessments) do not apply until named assets are registered.

Priority: Medium.

D.1.2.4 4. Cross-Asset Governance at the Boundaries

The framework is strong within individual asset types but weak at the interfaces between them:

  • Data-to-model: Gold datasets feed Tier 1 models, but there is no mechanism for the data Steward to notify the modelling Steward when a Gold dataset is superseded. The model run record captures the dataset ID used, but there is no trigger to check whether that ID is still the current approved version.
  • Code-to-model: The Tool Register and Model Register are separate with no cross-referencing. If a Tier 1 R tool depends on the output format of a Tier 1 FMP model, that dependency is not captured anywhere.
  • Cross-language pipelines: A pipeline that uses both R and Python has no single point of governance accountability.

What is needed: A cross-asset dependency field in each register, or a connection register extended to cover data-to-model and tool-to-model links as well as model-to-model links. The MCP server’s get_connections tool and its unified register backend are the natural implementation vehicle.

Priority: Medium.

D.1.2.5 5. The Accepted File Types Chapter Functioned as a Technical Specification, Not a Governance Document

Resolved at v1.1

The Accepted File Types document has been moved to Appendix E and renamed File Format Reference. Normative requirements are now enforced through the domain governance documents (Hydrometric Data Framework, R Tool Governance, Python Tool Governance) where roles and escalation paths already exist. Format compliance is checked automatically by the fw-governance MCP server check_file_formats tool.

Chapter 2 defined formats but assigned no roles, no enforcement mechanism, no approval gate, and no escalation path. If someone stored data as CSV instead of the required Parquet format, there was no mechanism in the framework for anyone to detect, report, or resolve it. Every other chapter had clear accountability; this one had none.

Resolution: Moved to Appendix E. Normative rules retained in domain chapters. MCP tooling provides automated enforcement.

D.1.2.6 6. Owner Accountability is Structurally Thin

The Owner (Deputy Director) is required to approve Tier 1 promotions, Gold datasets, Poor/Critical model conditions, AI service access, external data sharing, disposal, and the annual framework review. However, the Owner has no required training beyond a brief core module covering governance obligations, no required attendance at any review meeting, and no required interaction with any register or report beyond receiving the quarterly summary.

In practice this creates a risk that the Steward makes real decisions and the Owner rubber-stamps them, which would undermine the governance model the framework depends on. The framework has grade requirements for Steward (G7) and Custodian (any), but no substantive engagement requirements for the Owner beyond sign-off.

What is needed: A brief Owner engagement checklist as part of the annual review, for example confirmation that the Owner has reviewed the quarterly summary, can name the Tier 1 assets in their domain, and has seen the condition ratings for those assets.

Priority: Low. More a maturity improvement than a structural gap.

D.1.2.7 7. Incomplete Sections Undermine Credibility

Several passages in the current draft are working notes rather than governance text:

  • Chapter 6, §2.3: SEE BLACK BOX DOCUMENT ALAN SENT ME
  • Chapter 6, §5.1: is this done anywhere? (inline in a table)
  • Chapter 6, §7.2: (probably need a better name) in a section heading
  • Chapter 4, §7.1: Python onboarding section marked To be written
  • Chapter 3, Flode module table: NEEDS MODIFICATION
  • Multiple review dates remain as [Insert Date]

These are normal in a working draft, but they must be resolved before the document is circulated beyond the immediate authoring team. A Custodian reading the Black Box governance text should not encounter a note referencing a document sent by a colleague.

Priority: High. Resolve before circulation for formal review.

D.1.2.8 8. No Version Control Policy for the Framework Itself

Resolved at v1.4

A Framework Version Control subsection has been added to the Review and Compliance section. It defines three change categories (editorial, substantive, major), the approval route for each, the versioning convention (MAJOR.MINOR with _quarto.yml as master), and the team notification requirement for substantive and major changes.

The framework mandates version control for every other asset type but has no equivalent policy for changes to the governance documents themselves. What happens between annual reviews? Who approves minor corrections? How are changes to companion documents tracked against the parent framework version? The alignment register tracks divergences against external policy but not internal amendments.

What is needed: A brief change control section (perhaps in the Review and Compliance section) covering who may make corrections between reviews, what level of change triggers a version increment, and how changes are communicated to the team.

Priority: Low.

D.2 Proposed Change: Implementation Chapter

Based on the assessment above, a dedicated implementation chapter is proposed as either Chapter 8 or a new companion document. Its purpose would be to bridge the gap between what the framework requires and how a team beginning from the current state can actually put it into practice.

Proposed scope:

Section Content
Effective date and transition When the framework formally comes into force; phased compliance targets for Year 1, Year 2, and steady state
Register setup Format decisions (spreadsheet, YAML, Delta table), storage location, access, initial population process
Templates and worked examples A completed Tool Register entry, a completed run record, a completed condition assessment, a provenance record; for real or illustrative assets
MCP tooling How the fw-governance MCP server (see the MCP server specification) automates compliance checks, register drafting, and Steward reporting, and how this reduces the manual burden identified in weakness 3 above
Phased obligations Which governance obligations apply from day one, which require populated registers before they are meaningful, and which await MCP tooling
Getting to steady state What the governance system looks like when all Tier 1 assets are registered, all registers are current, and all automated checks are running, and a realistic path from here to there

The MCP server specification is the technical foundation for automating the bulk of the administrative burden. Specifically:

  • governance_summary and audit_tier1 automate the quarterly and annual Steward reporting obligations
  • check_tier_compliance and pre_review automate the mechanical portions of code review
  • validate_bronze_ingestion, check_silver_readiness, and check_gold_readiness automate data promotion checks
  • generate_run_record removes the friction of completing run records from scratch
  • scaffold_tool and generate_header make correct-by-default tool creation the path of least resistance

An implementation chapter should make explicit which governance obligations the MCP server reduces, so that teams and Owners understand the resourcing assumptions embedded in the framework’s review cadence.
