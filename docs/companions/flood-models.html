10 Purpose

This document sets out detailed governance standards for the flood models used and maintained by the Forecasting and Warning (F&W) team. It covers Flood Modeller Pro hydraulic models, PDM rainfall-runoff models, Black Box elements, and the boundary conditions that connect them. It is a companion to the Data and Digital Asset Governance Framework, which sets out the broader roles, tier system, and version control principles that apply to all team assets.

Two areas are given particular attention here. First, model condition: a structured way of assessing how fit for purpose a model is over time, accounting for factors beyond operational performance alone, including age, data currency, structural integrity, and known deficiencies. Second, model connections: how models are linked together in cascading systems, where the outputs of one model become the inputs to another, and what governance is required to keep those connections auditable and reliable.

This document is not a guide to modelling practice. It does not prescribe how to build, calibrate, or configure a model. Its concern is the other side of that work: how models are recorded, assessed, connected, and kept accountable over time, and what level of oversight each type of model requires.

11 1. Scope

This framework applies to all flood models used by the F&W team in operational forecasting, model development, or research activities, including:

  • Flood Modeller Pro (FMP) 1D and 2D hydraulic models

  • PDM (Probability Distributed Model) rainfall-runflow configurations and parameter sets

  • Black Box models, including neural network and transfer function models used in operational forecasting

  • Boundary condition datasets: upstream inflows, tidal boundaries, lateral inflows, reservoir operating rules, and any other forcing data used to drive model runs

  • Coupled and cascading model systems where outputs from one model type feed directly into another

  • Model calibration and validation records

Out of Scope Code tools used to run, process, or post-process model outputs are governed by the R and Python Tool Governances. Hydrometric │ input data used for calibration is governed by the Hydrometric Data Framework. This document covers the models themselves and the connections between them.

12 2. Model Types and Responsibilities

The team operates four categories of flood model. Each has distinct governance needs reflecting its structure, how it is calibrated, and how it sits within the broader modelling system.

12.1 2.1 Flood Modeller Pro (FMP) Hydraulic Models

FMP models simulate the movement of water through river channels and floodplains using 1D network schemes, 2D domain solvers, or linked 1D-2D configurations. They are the core hydraulic routing tools in the team’s operational system. For flood forecast modelling requirements we limit our use of these to1D simulations only, but also implement hydrological routing elements too such as Muskingum Cunge and it’s variable parameter variant.

FMP models require formal version control because they contain binary and configuration files that can change with each calibration update, boundary condition change, or software upgrade. A model that produces a formal output and a model that has been subsequently updated must both be retained, with the version used for each output clearly identified.

All FMP model files must follow the folder structure and naming conventions in the parent framework (Section 6). The Custodian is responsible for keeping model files in the agreed location and not on local machines or unmanaged drives.

12.2 2.2 PDM Rainfall-Runoff Models

PDM models transform rainfall and potential evapotranspiration inputs into catchment runoff, which is then used as an inflow boundary to FMP hydraulic models or fed directly into operational forecasting systems. PDM configurations include a parameter set, a calibration record, and specification of the input data sources used.

Parameter sets are particularly sensitive assets. A parameter set produced by one analyst using one period of observed data may produce materially different outputs from a parameter set calibrated by a different analyst on a different period, even for the same catchment. This makes version control and calibration documentation critical.

Every PDM parameter set must be stored in the agreed repository rather than on individual machines. It must be named following the standard convention set out in the parent framework and accompanied by a calibration record covering the period, data sources, performance metrics, and any known limitations.

12.3 2.3 Black Box Methods

Black Boxes are data-driven models that relate inputs directly to outputs without representing the physical processes in between. In the team’s operational context this includes transfer functions that route gauged flows between sites and regression-based routing models trained on historical observed records.

Black Box models carry a specific governance risk: because their internal workings are not as easily physically interpretable, it can be difficult to identify when a model has become unreliable. The model condition framework in Section 4 is particularly important for Black Box models, as performance degradation may not be apparent until a significant event occurs.

All Black Boxesused in operational forecasting are Tier 3 assets. They must have a named Custodian, a documented training dataset, and a formal condition assessment on the schedule defined in Section 4.

12.4 2.4 Boundary Conditions

Boundary conditions are the forcing inputs that drive model runs: upstream flow inflows, tidal water levels at downstream boundaries, lateral inflows from ungauged catchments, reservoir release rules, and operational interventions such as gate settings. They are distinct assets from the models themselves and require their own version control and documentation.

A boundary condition dataset is not simply a data file. It represents a set of decisions about what inputs are appropriate for a given model and scenario. Those decisions must be documented so that a model run can be reproduced and audited.

Boundary type Source Governance requirement
Upstream inflow PDM output, gauged flow (Gold tier), or routed flow from upstream FMP model Dataset ID and version recorded in run record; PDM parameter set version noted if PDM-derived
Tidal boundary MO and NOC tidal predictions and surge forecasts, EA/UKCFF /NRW/SEPA observed Supplier and product version noted; Gold-tier observed data where used for calibration
Lateral inflow Ungauged catchment estimate, PDM sub-catchment, or simplified rainfall-runoff Method documented; any simplifying assumptions explicitly stated in run record
Structure and reservoir operating rules Agreed operating procedure document, version-controlled Version of operating rules noted; any deviation from standard rules flagged in run record
Tidal flap / gate settings Asset configuration record or operational instruction Source and date of configuration noted; operational changes logged if applied mid-run

13 3. Model Register

Every flood model used by the team must be entered in the Model Register at the point it is used in a formal output or shared with another team member. The register is version-controlled and held in the team repository. It is distinct from the Tool Register in the parent framework, which covers code tools; the Model Register covers the hydraulic and hydrological models themselves.

The Steward is responsible for keeping the Model Register current. It must be updated whenever a model changes tier, a new calibrated version is produced, a model’s condition rating changes, or a model is deprecated.

14 4. Model Condition

Model condition is an assessment of how fit for purpose a model is at a given point in time. It is distinct from model performance in a narrow operational sense. A model may still produce outputs within acceptable error bounds while being in poor condition: its input data may be out of date, its channel geometry may no longer reflect the physical system, its software version may be unsupported (assuming changes to FM module adaptor), or its calibration may have been carried out on data that does not represent current catchment behaviour.

Condition assessment is the mechanism by which the team identifies models that need investment before problems emerge in operational use, rather than after. It provides an auditable basis for prioritising model maintenance work and for informing decisions about when a model should be retired or rebuilt.

14.1 4.1 Condition Factors

Model condition is assessed across five factors. Each factor is scored on a three-point scale: Good (2), Adequate (1), or Poor (0). The overall condition rating is the sum of the five scores, giving a range from 0 (critically poor) to 10 (fully current).

Factor Good (2) Adequate (1) Poor (0)
Data currency All input data sources current; rating curves reviewed within 3 years; boundary conditions reflect current system One or more input data sources older than 3 years or flagged for review; rating curve review overdue Input data materially out of date; rating curves known to be invalid; boundary conditions do not reflect current system
Structural integrity Channel geometry surveyed within 5 years or no significant physical changes known; mesh and network validated against current system Survey more than 5 years old but no significant physical changes identified; minor known discrepancies Survey known to be materially out of date; significant physical changes (flood defence works, channel modifications) not incorporated
Calibration currency Calibrated against events including at least one event within the last 5 years; performance metrics meet agreed thresholds Last calibration event more than 5 years ago but no evidence of performance degradation; metrics within acceptable range Calibration based solely on old events; performance against recent events below agreed thresholds; known deficiencies not addressed
Software and dependency currency Running on a current supported software version; all dependencies maintained and tested One version behind current release; dependencies functional but flagged for upgrade Running on an unsupported or deprecated software version; known compatibility issues with current infrastructure
Documentation completeness Full calibration record, run records, and model notes up to date; handover note current; all known issues logged Calibration record present but not fully updated after recent changes; run records incomplete for some outputs Calibration record missing or materially out of date; run records absent; no handover note

14.2 4.2 Condition Ratings

Score Rating Required action
9-10 Good Routine monitoring. Review on standard cycle (see Section 4.3).
7-8 Satisfactory No immediate action required. Identify improvement actions in the next maintenance cycle. Flag any Poor-scoring individual factors for attention.
5-6 Requires attention A condition improvement plan must be agreed with the Steward within three months. The model may continue in operational use while the plan is active, with the Steward’s agreement. Known deficiencies must be noted in all run records.
3-4 Poor Owner must be notified. A formal review is required within one month to decide whether the model continues in operational use, is suspended pending improvement, or is retired. Continued use requires Owner sign-off with documented rationale.
0-2 Critical Model is suspended from operational use immediately pending Owner review. Emergency improvement or replacement is required. Route D (emergency) from the parent framework applies if urgent operational cover is needed.

14.3 4.3 Review Schedule

Condition assessments are carried out on a rolling schedule. The schedule is set by the Steward and recorded in the Model Register.

Tier Standard review cycle Triggered review
Tier 3 - Operational Annual After any significant flood event where model performance can be assessed; after any physical change to the modelled system; after a software upgrade; on handover of custodianship. Automated methods can be introduced.
Tier 2 - Analytical Every two years After significant physical changes; after a major data update; on handover of custodianship
Tier 1 - Experimental On promotion to Tier 2 or above At the Steward’s discretion

A triggered review does not reset the standard cycle clock. A model that receives a triggered review in month six of a twelve-month cycle is still due its standard review at month twelve unless the Steward decides otherwise.

14.4 4.4 Condition and Model Connections

Where a model in poor condition provides inputs to downstream models, the condition risk propagates. If a PDM with a Poor calibration currency rating drives the upstream boundary of an FMP model, the FMP model’s outputs carry the same uncertainty regardless of the FMP model’s own condition score. The model connections register (Section 5) must be consulted during every condition assessment to identify whether a model’s condition affects connected models, and this must be recorded in the condition assessment note.

15 5. Model Connections

Flood forecasting systems are rarely a single model in isolation. In most catchments, the team operates cascading systems: PDM models produce catchment runoff that drives FMP hydraulic models; FMP models route flows downstream to become boundary conditions for further FMP models; tidal models set downstream boundaries for fluvial models; Black Boxes route flows between points or create behaviors that can’t be replicated in our hydraulic models.

Understanding these connections is essential for three reasons. First, an error or condition problem in an upstream model propagates downstream and affects every connected model’s outputs. Second, when a model is updated or recalibrated, the team needs to know which downstream models may be affected. Third, in an operational failure, knowing the connection structure allows the team to identify workarounds or manual overrides that maintain forecast coverage.

15.1 5.1 Connection Types

Connection type Description Example
Upstream inflow Output from one model (PDM runoff or upstream FMP routed flow) becomes the upstream boundary condition for a downstream model PDM catchment runoff feeds FMP river reach as a lateral inflow
Downstream boundary Output or agreed condition from one model sets the downstream boundary for another Tidal model water levels set the downstream boundary for an FMP estuarial reach
Intermediate routing A Black Box or simplified routing model transfers flows between two FMP reaches where a full model is not available Transfer function routes gauged flow from one site to the upstream boundary of an FMP model
Ensemble feed Multiple model instances or ensemble members provide probabilistic inputs to a downstream system NWP ensemble rainfall feeds multiple PDM runs, whose spread of outputs drives an ensemble of FMP runs

15.2 5.2 Connection Register

Every operational connection between models must be recorded in the Connection Register. This is a single version-controlled file held alongside the Model Register. The Steward is responsible for keeping it current. It must be updated whenever a model is added, modified, or retired, and whenever a connection changes.

Field Description
Connection ID Unique identifier: [UpstreamModelID]TO[DownstreamModelID] (e.g., SEVERN_PDM_v2.1_TO_SEVERN_FMP_v3.2)
Upstream model Model ID of the model providing the output
Downstream model Model ID of the model receiving the input
Connection type From the types defined in Section 5.1
Output variable What the upstream model provides (e.g., routed flow at [gauge], water level at [node])
Input variable How that output is used by the downstream model (e.g., upstream inflow boundary at node X)
Transfer method How the output reaches the downstream model: direct file transfer, API call, manual copy, Flode pipeline step
Time offset Any lag or lead time applied between the upstream output and the downstream input
Manual override Whether an override point exists; if so, who can authorise and action it
Failure mode What happens to the downstream model if this connection fails or the upstream model produces no output
Status Active, Suspended, or Deprecated

15.3 5.3 System Diagrams

The Connection Register is the authoritative record of model connections, but a system diagram showing the full cascade is required for every operational catchment or group of connected catchments. The diagram must show each model node, the direction of data flow, the connection type at each link, and any manual override points.

System diagrams are stored in the docs/ directory of the relevant model repository and must be updated whenever the Connection Register is updated. They do not need to be detailed engineering drawings: a clear flowchart identifying each model, its type, and the connections between it is sufficient. The Custodian produces and maintains these diagrams; the Steward reviews them as part of the annual audit if any modifications have been made.

15.4 5.4 Impact Assessment for Model Changes

Before any change to a model is deployed, the Custodian must consult the Connection Register to identify all downstream models that receive inputs from the model being changed. The impact assessment must consider:

  • Whether the output format, units, or temporal resolution of the upstream model changes in a way that the downstream model does not expect

  • Whether the recalibrated or updated upstream model produces materially different outputs under the conditions the downstream models are designed for

  • Whether any manual override points need to be adjusted

  • Whether the condition assessment for downstream models needs to be updated to reflect the changed upstream input

For Tier 3 models, the impact assessment is a required step before a pull request is merged and before a new model version is deployed to the operational environment. It must be documented in the run record or change log for the upstream model being updated.

16 6. Model Run Records

For every model run that produces a formal output such as performance testing, the Custodian must complete a run record. This is the mechanism by which any output can be traced back to the exact model version, input data, and boundary conditions used to produce it.

Field Description
Run ID Unique identifier for this run: [ModelID][YYYYMMDD][RunType]
Model ID and version Exact version of the model used (from the Model Register)
Run type Operational forecast, hindcast, scenario, calibration, or validation
Run date and time When the run was initiated and completed
Run by Name of the Custodian who ran the model
Input data Gold or Silver dataset IDs and versions for all hydrometric inputs; PDM parameter set version if PDM-derived inflows used
Boundary conditions Description and version of all boundary condition datasets used (see Section 2.4)
Connection overrides Any manual override points activated; what value was used and why
Software version Flood Modeller Pro build number or equivalent
Model condition at time of run Current condition rating and date of last assessment
Known deficiencies Any active condition concerns or known model limitations relevant to this run

Warnings and errors Any warnings, errors, or unexpected behaviour observed during the run
Notes Anything the analyst considers relevant to interpreting the outputs
Run records are stored in the /docs directory alongside the model project files. For Tier 3 operational runs, the Steward is notified of any run where a manual override was used or where model warnings were observed.

17 7. Calibration and Validation

Calibration is the process of adjusting model parameters so that simulated outputs match observed data. Validation is testing those parameters against observed data not used in calibration. Both are required before a model can be promoted to Tier 3 and must be repeated whenever the model is significantly updated.

17.1 7.1 Calibration Records

Every calibrated model version must have a calibration record. This is distinct from and complementary to the run records produced during the calibration process itself.

Field Description
Model ID and version The model version produced by this calibration
Calibration period Start and end dates of the period used for calibration
Events used List of flood events used, with dates and peak flow or level at key sites
Observed data sources Gold dataset IDs and versions for all observed data used; rating curve versions noted
Performance metrics Results at each calibration site: NSE, KGE, FAR, or equivalent; peak timing error; peak magnitude error
Validation period Start and end dates of the period used for validation
Validation performance Same metrics as calibration, applied to the validation period
Parameter changes from previous version What was changed and the justification
Known limitations Conditions or event types where the calibration is known to perform less well
Calibrated by Name of the Custodian who carried out the calibration
Reviewed by Name of the Steward who reviewed and approved the calibration
Date approved Date the Steward confirmed the calibration met the required standard

17.2 7.2 Calibration Performance Standards

The Steward defines and maintains performance thresholds for each model type and each key site. These thresholds form part of the condition assessment (Section 4) and the calibration approval process. A calibration that does not meet thresholds at any key site must be reviewed by the Steward before the model version is approved for operational use.

Thresholds are stored in the Model Register alongside each model’s entry and reviewed as part of the annual audit. Where a threshold is relaxed for a specific model or site, the Owner must approve the relaxation and the reason must be recorded.

18 8. Model Tier Promotion and Deprecation

A model moves between tiers as its use becomes more established or as it is superseded. Promotion and deprecation follow the same principles as the tool tier system in the parent framework, with the additions below specific to flood models.

18.1 8.1 Promotion to Tier 3

Promotion of a model to Tier 3 operational status requires:

  • A complete calibration record meeting performance thresholds at all key sites

  • A condition assessment with a rating of Satisfactory (7-8) or above

  • All connections to and from the model documented in the Connection Register

  • A system diagram current and reviewed by the Steward

  • A handover note or runbook sufficient for another team member to run the model operationally

  • Owner sign-off

Promotion to Tier 3 does not mean the model will not change. It means that changes to a Tier 3 model follow the full change process including impact assessment, run record, and Steward review before deployment.

18.2 8.2 Deprecation

A model is deprecated when it is replaced by a newer version or an alternative model, or if the operational need it served no longer exists. Deprecation requires Owner approval. A deprecated model’s files are retained and its status in the Model Register is set to Deprecated. The previous version is never deleted: it is the record of what produced historical outputs.

Where a deprecated model provided inputs to downstream models, the Connection Register must be updated before deprecation is confirmed and the downstream models’ run records must note the change in upstream input from the date of deprecation.

19 9. Custodianship

The Owner, Steward, and Custodian roles from the parent framework apply to all flood models. The following additions are specific to this document.

For coupled or cascading systems, custodianship is assigned separately for each model component. Where one person is the Custodian for both an upstream and a downstream model, the Steward must satisfy themselves that there is sufficient independent oversight of the connection between them. For Tier 3 cascades involving more than three connected models, the Steward should consider whether a dedicated system-level Custodian is warranted.

Responsibility Role
Keep Model Register current Steward
Keep Connection Register current Steward
Maintain system diagrams Custodian (production), Steward (review)
Carry out and document condition assessments Custodian (assessment), Steward (review and sign-off)
Complete run records for all formal outputs Custodian
Notify Steward when condition rating drops to Requires Attention or below Custodian
Notify Owner when condition rating reaches Poor or below Steward
Impact assessment before deploying model changes Custodian (draft), Steward (review for Tier 3)
Annual audit of all Tier 3 models Delegated Steward
Owner sign-off for Tier 3 promotion, deprecation, or continued use of a Poor-rated model Owner

20 10. Review and Compliance

This document is reviewed annually alongside the parent framework and companion documents. The review is led by the Steward with Owner sign-off. The annual review considers:

  • Whether the condition factor definitions and scoring thresholds remain appropriate

  • Whether performance thresholds for calibration approval need updating

  • Whether the Connection Register is current and reflects the operational system

  • Model condition trends: are ratings improving, stable, or degrading across the portfolio?

  • Any operational events in the preceding year where model condition or connection failures contributed to forecasting uncertainty

  • Feedback from Custodians on what is working and where the framework needs adjustment

The Delegated Steward conducts an annual audit of all Tier 3 models covering: condition rating currency, calibration record completeness, run record completeness for all formal outputs, Connection Register accuracy, and system diagram currency. Findings are reported to the Owner alongside the wider governance audit.

Exceptions process, escalation paths, and compliance requirements: see Data and Digital Asset Governance Framework v2.0, Section 11.

22 Appendix A - Glossary

Term Definition
FMP Flood Modeller Pro - the team’s primary hydraulic modelling software for 1D and 2D flood simulation
PDM Probability Distributed Model - a conceptual rainfall-runoff model that converts rainfall and evapotranspiration inputs into catchment runoff
Black Box model A data-driven model that relates inputs directly to outputs without representing physical processes; includes neural network and transfer function models
Boundary condition An input that defines the forcing conditions at the edge of a model domain: upstream inflows, downstream water levels, lateral inflows, or operational settings
Cascading system A modelling system where the outputs of one model become the inputs to one or more downstream models
Model condition An assessment of how fit for purpose a model is, based on data currency, structural integrity, calibration currency, software currency, and documentation completeness
Condition rating The numerical score (0-10) produced by a condition assessment, mapped to a descriptive rating from Critical to Good
Connection Register The version-controlled record of all active connections between models in the team’s operational system
Model Register The version-controlled record of all flood models held or used by the team, including their tier, condition rating, and connection references
Run record The documented record of the inputs, versions, boundary conditions, and outputs for a specific model run
Calibration record The documented record of the data, events, methods, and performance metrics for a specific model calibration
NSE / KGE / FAR Common hydrological performance metrics: Nash-Sutcliffe Efficiency, Kling-Gupta Efficiency, False Alarm Ratio
Manual override point A defined point in a cascading system where an operator can substitute a model output with an observed or manually estimated value
Triggered review A condition assessment carried out in response to a specific event rather than on the standard review cycle
