9 1. Purpose

The Flood Forecast Modelling (FFM) and Warning teams import hydrometric data - flow, stage, and rainfall records - from a range of internal systems (Hydrology Data Explorer and WISKI) as well as external suppliers including SEPA, NRW, Met Office, and other partner organisations. These data are the foundation of everything the team does: they drive model calibration, feed operational forecasts, validate modelling outputs, and inform flood risk decisions.

Without a clear framework, the risks are real: data used at different stages of processing gets confused with raw data, quality problems go unnoticed until they affect a model output, provenance is lost making it impossible to audit where a number came from, and the same cleaning work gets done repeatedly by different people with different results.

This framework addresses those risks by defining how imported hydrometric data moves through three quality tiers: Bronze, Silver, and Gold - from raw ingestion to analysis-ready products. It sets out who owns and is responsible for data at each tier, how quality is assessed and recorded, how provenance is tracked, how data is stored, and how data quality is improved over time.

This framework is a companion to the Data & Digital Asset Governance Framework v2.0, which sets out the Owner, Steward, and Custodian roles and governance principles that apply here. The roles used in this document follow that framework.

9.1 2. Scope

This framework covers all hydrometric data imported and used by the Flood Forecast Modelling Team, including:

  • River flow and water level records from gauging stations (telemetry and archived)

  • Rating metadata

  • Rainfall records from rain gauges and gridded weather radar products

  • Catchment-averaged rainfall products

  • Snow measurements

  • MOSES PE and similar products

  • Soil moisture data e.g. Copernicus

  • Historical event datasets used for model calibration and validation

Out of Scope: Model outputs, internally generated datasets (e.g., ensemble forecasts), and data produced by the team’s own tools are governed by the Data & Digital Asset Governance Framework and are not covered here. Internally generated data does not pass through the Bronze to Silver to Gold pipelines.

10 3. The Medallion Data Framework

The parent framework (Chapter 2) defines two distinct classification systems that apply to all team assets. The operational tier system (Tier 3, 2, 3) answers the question: how critical is this asset to the live forecasting service? The medallion architecture (Bronze, Silver, Gold) answers a different question: how far has this data progressed through the quality assurance process?

For code tools and models these two dimensions often align closely. For hydrometric data they are genuinely independent, and that independence matters. A Silver dataset for the River Wye may be used in a Tier 2 post-event analysis today and promoted to supply a Tier 3 operational model tomorrow, without changing anything about the data itself. A Gold approved benchmark series for a small catchment may only ever be used in Tier 1 research. The operational tier describes the use; the medallion tier describes the data’s quality state. Conflating them would mean re-approving data every time its purpose changes, which is neither practical nor meaningful.

The medallion architecture was developed in data engineering for exactly the problem the team faces: data arriving from multiple external sources, at different quality levels, needing to flow through defined processing stages before being fit for production use. It maps directly onto the hydrometric data lifecycle. Supplier data arrives raw and unmodified (Bronze). The team applies quality control, flags anomalies, applies rating curves, and documents decisions (Silver). Derived products, aggregated statistics, calibration benchmarks, and ML training sets are assembled from Silver and formally approved (Gold). Each stage represents a distinct level of trust and a distinct degree of accountability. Bronze data is not worse than Silver data; it is simply at a different stage. Storing them as separate, preserved states makes that explicit.

Taken together, the two frameworks give the team three things it cannot get from informal arrangements. Reproducibility: any formal output can be traced back through Gold to Silver to Bronze to the exact file received from the supplier, with every quality decision recorded along the way. Efficiency: QC work invested at Silver is done once and available to everyone, rather than each analyst reworking the same dataset for their own purpose and potentially reaching different conclusions. Confidence: a Gold product carries a specific meaning. It has passed through defined stages, had decisions documented, and been formally approved for an identified purpose. When a Gold dataset feeds a Tier 3 model run, the team knows precisely what it is, who reviewed it, and what it has been approved for. That chain of accountability is the point.

Imported hydrometric data passes through three tiers of increasing quality and fitness for purpose. The tiers are named Bronze, Silver, and Gold - a medallion structure adapted from data engineering practice to suit hydrological data management.

The key principle is that each tier is a distinct, preserved state. Data is never overwritten in place. Moving data to the next tier creates a new dataset; the previous tier is always retained. This means the team can always trace exactly what was received, what quality decisions were made, and what version of a dataset fed a particular model run.

Tier What it contains Who uses it
Bronze: Raw Data exactly as received from API calls, manual imports, or directly from suppliers. No edits, no corrections. Even obvious errors are preserved. Fully provenance-labelled. Custodians (ingest), Stewards (audit). Not used directly in modelling.
Silver: Quality Controlled Bronze data that has been checked, flagged, gap-assessed, and where appropriate corrected or gap-filled. All changes are recorded with reasons. Rating curves applied for flow. Modelling custodians and data analysts. The primary source for model calibration and validation.
Gold: Analysis-Ready Derived products from Silver data: aggregated statistics, design event datasets, approved benchmark series, multi-site composite records, and ML training sets at native 15-minute resolution with static attributes attached. Formally approved for operational use. Modelling custodians and data analysts. AI/ML training sets (at native resolution with static attributes attached), formal outputs, published datasets, design work.

11 4. Bronze Tier - Raw Ingested Data

BRONZE - Raw, immutable, fully provenance-labelled Bronze data is the unmodified record of what was received from the supplier. Nothing is corrected, removed, or reformatted beyond what is strictly necessary to store it. Every Bronze dataset must be treated as read-only from the moment of ingestion.

11.1 4.1 Ingestion Requirements

When a new dataset is received, the Custodian must complete all of the following before the data is stored:

  • Assign a unique dataset ID using the standard format: [SupplierCode][SiteID][DataType]_[YYYYMMDD] (e.g., EA_39001_Q_20260115)

  • Record the full provenance record (see Section 11.2) in the Hydrometric Data Register via reach.io’s write_provenance_record() function

  • Store the data in the Bronze layer of the team’s data store using reach.io’s directory structure (created by setup_hydro_store()); do not modify the file

  • Apply the Bronze schema using apply_bronze_schema() to enforce the six mandatory columns (timestamp, value, supplier_flag, dataset_id, site_id, data_type) and correct data types

  • Check the file opens and is readable; record any format issues in the provenance record

  • Notify the Steward that a new Bronze dataset has been ingested

For API-sourced gauges registered in the Gauge Registry, reach.io’s run_backfill() and route_gauge() functions automate the fetch, schema application, and provenance recording steps. The Custodian is still responsible for reviewing the resulting register entry and confirming completeness.

Bronze data must never be modified after ingestion. If a supplier sends a corrected version of a dataset, the corrected version is ingested as a new Bronze dataset with its own dataset ID and provenance record, referencing the original.

11.2 4.2 Provenance Record

Every Bronze dataset must have a complete provenance record in the Hydrometric Data Register (Chapter 17). This is the single most important thing recorded at Bronze - without it, no downstream use of the data can be properly audited. See Section 17.1 for the full field list.

The key fields recorded at ingestion are: dataset ID, supplier, site identifier, data type, time period, temporal resolution, units, datum or rating reference, file format as received, date received, received by, method of receipt, any supplier quality flags and their meaning, known limitations stated by the supplier, file path, and any notes on unusual aspects of the delivery.

11.3 4.3 Ownership at Bronze

The Custodian who ingests the data holds Bronze custodianship. They are responsible for completing the provenance record and storing the data correctly. The Steward is responsible for checking that provenance records are complete and that Bronze data is not being modified.

Bronze data is owned by the team collectively - it represents an external input and no individual team member has the right to modify or delete it. Deletion of Bronze data requires Owner approval and must be documented.

4.4 What Bronze Data Is Not For

Bronze data is an archive, not a working dataset. It should not be:

  • Used directly as input to a model or analysis without Silver processing

  • Shared externally (the supplier’s data licence applies - check before sharing)

  • Modified to fix errors, even obvious ones

  • Used to draw conclusions about data quality without a Silver QC record

12 5. Silver Tier - Quality Controlled Data

SILVER - Checked, flagged, corrected where appropriate, fully documented Silver data is the result of applying a documented quality control process to Bronze data. Every change from Bronze to Silver is recorded - what was changed, why, who made the decision, and what evidence supported it. Silver is the primary working dataset for modellers and analysts.

12.1 5.1 The QC Process

Quality control must be completed by a Custodian and reviewed by the Steward before data is promoted from Bronze to Silver. The QC process covers four stages:

12.1.1 Stage 1: Automated Checks

Run automated checks to identify obvious problems. These checks do not change any values - they produce a flag dataset stored alongside the data. Automated checks include:

  • Range checks: values outside physically plausible bounds for the variable and site (e.g., negative flow, unrealistic stage)

  • Rate-of-change checks: implausible step changes between consecutive time-steps

  • Flatline detection: sequences of identical repeated values (sensor malfunction indicator)

  • Gap detection: missing values, irregular time-steps, or gaps relative to the stated period

  • Duplicate detection: repeated timestamps

  • Consistency with supplier flags: values flagged as poor quality by the supplier

12.1.2 Stage 2: Visual and Expert Review

A Custodian with appropriate domain knowledge reviews the flagged data. For flow and level data this includes checking against nearby gauges, upstream/downstream consistency, and known events. The review produces:

  • A revised flag dataset - each value receives a quality flag (see Section 12.2)

  • A review note for any value that is flagged as suspect or rejected

  • A rating curve assessment for flow data (see Section 12.3)

12.1.3 Stage 3: Gap and Error Handling

For each gap or rejected value, the Custodian must make a documented decision:

Decision When to apply
Retain as flagged The value is suspect but not clearly wrong; retain with a ‘suspect’ flag so downstream users can decide whether to use it
Reject and leave as gap The value is clearly wrong (e.g., sensor malfunction) and no suitable substitute is available; record the gap extent and reason
Gap-fill with documented method A gap can be filled using a defensible method (e.g., correlation with nearby gauge, simple interpolation for short gaps); the fill method, source data, and uncertainty estimate must all be recorded
Reject the entire dataset If data quality is too poor to be useful even with flagging, the dataset is rejected at Silver; document the reasons and retain Bronze

Gap-filling is only permitted where the method is documented and the filled values are clearly distinguishable from observed values. Over-enthusiastic gap-filling is a greater risk than gaps. When in doubt, flag and retain rather than fill.

12.1.4 Stage 4: Steward Review and Promotion

Before data is promoted to Silver, the Steward or Delegated Steward must review:

  • That the QC process has been followed and documented

  • That flagging decisions are consistent with team standards

  • That any gap-filling is justified and documented

  • That the Silver dataset ID and QC record are complete

The Steward records their approval in the Hydrometric Data Register. Only after Steward approval is the dataset status set to Silver.

12.2 5.2 Quality Flags

Every value in a Silver dataset carries a quality flag. The team uses the following flag scheme, which is compatible with the Environment Agency’s national flag convention:

Flag Label Meaning Use in modelling
1 Good Passed all automated checks; expert review confirms no concerns Use without restriction
2 Estimated Observed value is missing or rejected; value has been estimated using a documented method Use with caution; document in run records
3 Suspect Value appears anomalous but cannot be confirmed as wrong; retained for user judgement Exclude by default; include only if explicitly justified
4 Rejected Value is confirmed as erroneous; treated as missing Do not use
5 No data Timestep is genuinely missing with no basis for estimation Do not use
6 Below detection Value is below the instrument’s detection limit; record the limit Use as threshold information only

Flags must be stored as a separate column or parallel file - never overwrite the value itself. A flag of 2 (Estimated) must always be accompanied by an estimation method field.

12.3 5.3 Rating Curves and Flow Derivation

For stage (water level) data where the team derives flow using a rating curve, the Silver record must include:

  • The rating curve version used (name, version number, valid stage range, source/authority)

  • The date the rating curve was applied

  • Any values where stage falls outside the rated range, flagged separately as ‘extrapolated’

  • A note of any known shift events (e.g., channel changes, weed growth) that may affect the rating

Where the team uses supplier-derived flow directly (e.g., EA gauged flow), the supplier’s rating version must be recorded in the provenance record rather than applied by the team.

12.4 5.4 Silver Dataset Naming and Storage

Each Silver dataset gets its own dataset ID, linking it explicitly to its Bronze source:

Format: [BronzeDatasetID]_SILVER_v[N] Example: EA_39001_Q_20260115_SILVER_v1

When a Silver dataset is revised (e.g., following updated rating curve or additional QC), a new version is created. Previous Silver versions are retained. The QC record must note what changed and why.

12.5 5.5 Silver QC Record

Each Silver dataset must have a complete QC record in the Hydrometric Data Register (Chapter 17). See Section 17.1 for the full field list.

The key fields recorded at Silver promotion are: Silver dataset ID, Bronze source ID, Custodian who carried out QC, Steward who reviewed and approved, QC date, automated checks run and tool used, flag count summary by type, gap-filling method and extent if applied, rating curve version and valid range if applied, any remaining known issues, comparison datasets used during expert review, and file path.

12.6 5.6 Ownership at Silver

The Steward or Delegated Steward holds Silver ownership. They are accountable for the quality of Silver datasets and for ensuring QC records are complete and honest - including about limitations. The Custodian who carried out the QC is named in the record and is responsible for the decisions made during QC.

Silver data is the primary working dataset. Modellers and analysts should use Silver data and record which Silver dataset ID (and version) fed their work. If a modeller identifies a quality issue in Silver data, they must raise it with the Steward rather than correcting it locally.

13 6. Gold Tier - Analysis-Ready Products

GOLD - Formally approved, derived products ready for operational use Gold datasets are derived from Silver data. They are aggregated, summarised, combined, or formally approved at their native resolution to produce a specific analysis-ready product for a named purpose. Gold datasets require Owner approval and are the only tier that should be used in formal outputs, operational forecasting, ML model training intended for promotion, or external publications.

13.1 6.1 What Qualifies as Gold

A Gold dataset is a deliberate, named product created for a specific purpose. Examples include:

  • Catchment-averaged rainfall series constructed from multiple rain gauge Silver records

  • Multi-site composite records where gaps at one site are filled from a correlated site

  • ML training set: a named, approved collection of 15-minute Silver time series data with static catchment attributes attached, covering a defined period and gauge selection, with flag exclusion rules documented and Steward sign-off that Silver quality is sufficient for model training

  • Event hydrographs used in calibrations and post event analytics.

  • Aggregated data such as annual maximum flow series for a gauge used in flood frequency analysis

  • Daily mean flow record for a catchment, approved as the reference series for model calibration

  • Design event hydrograph derived from observed events in Silver data

  • Benchmark period dataset (agreed period used for inter-annual comparison)

Gold is not simply ‘better Silver’. It is a specific product with a defined purpose, a named user, and formal approval. Creating a Gold dataset is a decision, not an automatic step.

13.2 6.2 Creating a Gold Dataset

A Gold dataset must be proposed, documented, and approved before it is used:

  • Custodian or modeller proposes the Gold product, specifying: its purpose, which Silver datasets it draws from, the derivation method, and the intended use

  • Steward reviews the proposal and the underlying Silver data quality, particularly flag counts and known issues

  • Derivation is carried out and documented in a Gold derivation record (see Section 13.3)

  • Owner reviews and formally approves the Gold dataset before it enters operational use

  • Gold dataset is registered in the Hydrometric Data Register with status ‘Approved’

13.3 6.3 Gold Derivation Record

Each Gold dataset must have a complete derivation record in the Hydrometric Data Register (Chapter 17). See Section 17.1 for the full field list.

The key fields recorded when a Gold dataset is created are: Gold dataset ID, purpose and who approved it, Silver source dataset IDs and versions, derivation method (aggregation, merging, event extraction, or native resolution for ML training sets), Silver quality gate summary (flag counts, gap extent, known issues), any exclusions and the reason, Custodian or analyst who produced it, Owner approval name and date, intended use and any restrictions on use, expiry or review date, and file path.

13.4 6.4 Versioning and Supersession

When new Silver data becomes available, or when a quality issue is identified, a Gold dataset may need to be updated. A new version is created; the previous version is retained and its status changed to ‘Superseded’. Any model or analysis that used the superseded version must be flagged for review.

The Steward or Delegated Steward must be notified whenever a Gold dataset is superseded and must confirm whether dependent work needs to be revisited.

13.5 6.5 Ownership at Gold

Gold datasets are owned by the Owner and stewarded by the Steward. No one else can approve a new Gold dataset or change its status. This is the highest accountability level because Gold data directly informs business decisions, model calibration choices, and potentially regulatory outputs or KPIs.

13.6 6.6 ML Training Sets as Gold Products

Unlike most Gold products, an ML training set does not aggregate or reduce the underlying Silver data. It stays at the native 15-minute resolution. What makes it a Gold product is that it represents a set of deliberate, documented decisions about which data to use and how, combined with Steward confirmation that the Silver quality is sufficient for model training.

A Silver dataset is ready to become a Gold ML training set when all of the following conditions are met:

  • The time series data has been promoted to Silver and has a complete QC record including flag counts, gap assessment, and rating curve version where applicable

  • Static catchment attributes have been calculated and attached, covering at minimum: catchment area, BFI, mean elevation, dominant soil type, and land cover class

  • The training period has been defined and the flag exclusion rule has been documented (e.g., which flag types cause a timestep to be dropped from training)

  • Gap-filling decisions for the training period have been recorded, including method

  • and extent

  • The Steward has reviewed the Silver quality and confirmed it is sufficient for the intended model type and promotion tier

The Gold derivation record for an ML training set should describe the gauge selection rationale, the training period, and the static attribute sources alongside the standard fields. The derivation method field should state that no temporal aggregation has been applied and that the dataset is at native 15-minute resolution.

This training set Gold product type is distinct from other Gold types. It should not be used for flood frequency analysis or hydraulic model calibration, and those Gold products should not be used as ML training sets without a new Gold derivation record confirming suitability.

14 7. Parquet Storage Schema

All Bronze, Silver, and Gold datasets are stored as Parquet files. Parquet is the mandatory storage format for hydrometric time series data within the medallion architecture. It is used across the R tooling (via the arrow package) and the Python tooling (via polars or pyarrow), and it is the native format for the Databricks DASH environment.

Parquet stores data in a typed, columnar format that is efficient to read, write, and query even for very long time series. Unlike CSV, it preserves data types exactly (timestamps, integers, floats) and is compressed automatically, which matters for long multi-year records at 15-minute resolution.

All three tiers use Parquet. Bronze Parquet is the standardised ingest format derived from whatever the supplier sent. Silver and Gold Parquet add columns; they never remove or overwrite columns from the tier below.

For the rationale behind the Parquet requirement, partitioning guidance, format comparisons (including Delta tables, NetCDF, GeoParquet, and the CSV and Excel restrictions), see Appendix E. Parquet schema compliance for Bronze, Silver, and Gold datasets is checked automatically by the fw-governance MCP server validate_parquet_schema and validate_bronze_ingestion tools.

14.1 7.1 Why Parquet for Hydrometric Time Series

Reason Detail
Type safety Timestamps are stored as datetime64[ns, UTC] rather than strings. Floats are float64 throughout. Integers (flags, counts) are int32. This prevents silent type errors when data is read by different tools.
Columnar reads Downstream tools can read only the columns they need (e.g., just timestamp and value) without loading the full file. This is important for long records across hundreds of gauges.
Compression Parquet uses Snappy compression by default, reducing storage by 60-80% compared to equivalent CSV files with no loss of data.
Cross-tool compatibility The same Parquet file can be read by R (arrow::read_parquet), Python (polars.read_parquet / pyarrow), and Databricks (spark.read.parquet) without conversion.
Partition support Large datasets can be partitioned by supplier, site, or year, so queries only scan the relevant subset of files.

14.2 7.2 Bronze Parquet Schema

Bronze Parquet is produced at ingestion. The Custodian converts the supplier’s raw file into the team’s standard Bronze schema. The original raw file is also retained unchanged. All dataset-level metadata (supplier, time period, units, licence, file format, etc.) is recorded in the register, not repeated in the Parquet.

Mandatory columns:

Column Type Description
timestamp timestamp[ns, UTC] Observation datetime in UTC. Convert supplier local times at ingestion and record the offset in the register.
value float64 Observed value as received from supplier. Do not round or convert units. Preserve the supplier’s precision.
supplier_flag string Quality code or flag exactly as provided by the supplier. Null if the supplier provides no flags.
dataset_id string The Bronze dataset ID (e.g., EA_39001_Q_20260115). The join key to the register. Stored in every row so merged files remain traceable.
site_id string Supplier’s site identifier. Preserved exactly as received.
data_type string Data type code: Q, H, P, SM, or SWE.

Optional columns (include if provided by supplier):

Column Type Description
raw_value_str string The value as a raw string before parsing. Retain where the supplier uses special markers (e.g., “>” for above-range values).
uncertainty float64 Measurement uncertainty if stated by supplier.
sensor_id string Instrument or sensor ID where the supplier provides this.
Do not add any columns beyond those listed above to Bronze Parquet. Bronze is a faithful representation of what was received. Any derived or computed fields belong in Silver.

14.3 7.3 Silver Parquet Schema

Silver Parquet is derived from Bronze. It retains all Bronze columns and adds QC columns. Values and timestamps from Bronze are never altered - corrections and estimates are recorded in new columns, not by overwriting the Bronze value.

Added columns (in addition to all Bronze columns):

Column Type Description
qc_flag int32 Team quality flag (1=Good, 2=Estimated, 3=Suspect, 4=Rejected, 5=No data, 6=Below detection). See Section 12.2. Every row must have a qc_flag at Silver.
qc_value float64 The value to use for analysis. Equal to value for Good data. For Estimated rows, this is the gap-filled or estimated value. For Rejected or No data rows, this is null. Never overwrite value; always populate qc_value separately.
estimation_method string How qc_value was estimated for flag=2 rows (e.g., “linear_interpolation”, “correlation_gauge_39002”, “mean_seasonal”). Null for all other flags.
rating_curve_version string Version of the rating curve applied to derive flow from stage. Null for direct supplier flow or non-flow data types.
extrapolated bool True where stage falls outside the valid range of the rating curve. Null for non-flow data.
silver_dataset_id string The Silver dataset ID (e.g., EA_39001_Q_20260115_SILVER_v1). Stored in every row.
qc_version int32 Version number of the Silver dataset (1, 2, 3…). Increments when QC is revised.
The value column is always the Bronze value. The qc_value column is what modellers and analysts should use. Keeping both means the QC decisions are always auditable.

14.4 7.4 Gold Parquet Schema

Gold Parquet is derived from Silver. The schema depends on the Gold product type. Two standard structures are defined below.

Time Series Gold (calibration inputs, benchmark series)

For Gold products that are still time series (e.g., a daily mean flow series approved for model calibration), use the Silver schema with the following additional columns. Dataset-level approval details are held in the register, not repeated per row.

Column Type Description
gold_dataset_id string The Gold dataset ID (e.g., 39001_Q_GOLD_FFA_v1). Join key to the register. Stored in every row.
gold_version int32 Version number of the Gold dataset.
flag_exclusion_rule string The flag exclusion rule applied when deriving Gold from Silver (e.g., “exclude_flags_3_4_5”). Stored in every row so the rule is self-documenting even in extracted subsets.

The qc_value column from Silver is the source value for Gold time series. Rejected and No data rows (flags 4 and 5) are typically excluded; the flag_exclusion_rule column records exactly which flags were dropped.

Aggregated Gold (statistics, design events, frequency analysis inputs)

For Gold products that aggregate Silver time series into statistics or event summaries, use a purpose-specific schema. At minimum include:

Column Type Description
gold_dataset_id string Gold dataset ID. Join key to the register.
site_id string Site or catchment identifier
period_start date32 Start of the aggregation period
period_end date32 End of the aggregation period
[statistic columns] float64 e.g., annual_max_flow_m3s, peak_rainfall_mm, mean_daily_flow_m3s. Name columns with units as suffix.
data_completeness_pct float64 Percentage of the period covered by Good or Estimated Silver data (flags 1 and 2).
silver_source_ids string Pipe-separated list of Silver dataset IDs used (e.g., EA_39001_Q_20230101_SILVER_v1│EA_39001_Q_20240101_SILVER_v1). Keeps lineage readable in any tool.

14.4.1 ML Training Set Gold

For Gold ML training sets (Section 13.6), use the time series Gold schema with the following additional columns. Static catchment attributes are repeated on every row so a single Parquet file is self-contained for training without needing a join. Approval details are held in the register.

Column Type Description
training_set_id string Gold dataset ID for this ML training set (e.g., 39001_Q_GOLD_LSTM_v1). Join key to the register.
flag_exclusion_rule string Flag exclusion rule applied (e.g., exclude_flags_3_4_5). Stored in every row.
catchment_area_km2 float64 Catchment area in km².
bfi float64 Base Flow Index (0 to 1). Source and version held in the register derivation record.
mean_elevation_m float64 Mean catchment elevation in metres above ordnance datum.
dominant_soil_type string Dominant soil class from the HOST classification (e.g., HOST_1, HOST_29).
land_cover_class string Dominant land cover class (e.g., improved_grassland, arable, woodland). Source dataset in register.
gauge_easting float64 Gauge location easting in OSGB36 (metres).
gauge_northing float64 Gauge location northing in OSGB36 (metres).
Static attributes are repeated on every row so the file is self-contained for training. A pipeline loads one file and gets both the time series and catchment descriptors. The source dataset and version for each attribute must be recorded in the register derivation record, not in the Parquet itself.

For large datasets covering many sites or long time periods, Parquet files should be partitioned to avoid loading unnecessary data. The recommended partition scheme is:

Tier Partition by Example path
Bronze supplier / data_type / year bronze/EA/Q/2024/EA_39001_Q_20240101.parquet
Silver data_type / site_id silver/Q/39001/EA_39001_Q_20260115_SILVER_v1.parquet
Gold data_type / purpose gold/Q/FFA/39001_Q_GOLD_FFA_v2.parquet

Partitioning is mandatory for any dataset covering more than 50 sites or more than five years of 15-minute data. For smaller datasets, a single Parquet file per dataset ID is acceptable.

In Databricks, use Delta Lake tables rather than raw Parquet files for Bronze and Silver stores. Delta Lake provides transaction safety, schema enforcement, and time-travel queries on top of the Parquet format. The column schemas above apply to Delta Lake tables identically.

The Parquet schemas defined in this section are the interface contract between the Hydrometric Data Framework and the AI/ML Test Environment. The ML training pipeline reads Gold Parquet using the column names and types defined in Sections 7.3 and 7.4. Any schema changes must be agreed between the Steward and the Delegated Steward before implementation.

15 8. Data Quality Improvement

The medallion structure is not just a filing system; it is a mechanism for identifying and acting on data quality problems over time. Quality issues discovered at Silver or Gold should feed back into improved processes and, where possible, improved data from suppliers.

15.1 8.1 Flagging Systemic Issues

When a Custodian or Steward identifies a recurring quality problem - a gauge that consistently produces flatline values during high flows, a supplier format that loses trailing zeros, a rating curve that is clearly outdated - this should be escalated as a systemic issue rather than handled case by case. Systemic issues are recorded in the Data Quality Issue Log and assigned to the Delegated Steward to manage.

15.2 8.2 Supplier Engagement

Where a Bronze dataset contains quality problems that originate with the supplier (instrument failures, incorrect datum, outdated rating), the Delegated Steward should:

  • Document the issue precisely in the Silver QC record

  • Raise the issue with the supplier in writing, referencing the specific time periods affected

  • Request a corrected dataset where one is available

  • Record the outcome of the engagement in the Data Quality Issue Log

The team should not routinely correct supplier errors at Silver without engaging the supplier first, unless the operational need is urgent and documented. Correcting supplier errors silently means the supplier never improves.

15.3 8.3 Rating Curve Reviews

Rating curves age. Channel geometry changes after flood events, vegetation and weed growth affects stage-discharge relationships seasonally, and structural changes at gauging stations invalidate previous curves. The Delegated Steward is responsible for:

  • Maintaining a rating curve review schedule for all sites where the team applies its own rating

  • Flagging in the Silver record when a rating review is overdue

  • Requesting updated rating information from the gauge operators where the team relies on a supplier rating

  • Triggering a Silver version update whenever a new rating curve is applied

15.4 8.4 Data Quality Metrics and Reporting

The Steward produces a quarterly data quality summary covering:

  • Number of active Bronze datasets, Silver datasets (by flag profile), and Gold datasets

  • Datasets awaiting Silver promotion (backlog)

  • Open Data Quality Issue Log entries and their age

  • Supplier engagement outcomes in the quarter

  • Rating curves flagged as overdue for review

The summary is shared with the Owner and reported at the team’s quarterly governance review.

16 9. Provenance and Traceability

Every formal output the team produces must be traceable back to the data that fed it. The Bronze to Silver to Gold chain provides that traceability, but only if it is used consistently.

16.1 9.1 Dataset Lineage

For any Gold dataset, it must be possible to answer:

  • Which Bronze datasets contributed? What were their provenance records?

  • Which Silver processing steps were applied, and by whom?

  • What flags are present in the Silver data feeding this Gold product?

  • Has the supplier’s original data been corrected? If so, how, why, and by whom?

The Hydrometric Data Register (Chapter 17) maintains this lineage by linking Gold IDs to Silver IDs to Bronze IDs.

16.2 9.2 Recording Data Use in Model Runs

When a model run uses hydrometric data, the run record must specify:

  • The Gold or Silver dataset ID(s) used, including version

  • The time period extracted

  • Any flags excluded from the analysis and the exclusion rule applied

16.3 9.3 Retrospective Traceability

  • Bronze datasets are never deleted (see Section 18.1)

  • Silver versions are retained even when superseded

  • Gold versions are retained even when superseded, with their status changed to ‘Superseded’

  • The Hydrometric Data Register is backed up as part of the team’s standard data backup process

17 10. Hydrometric Data Register

The Hydrometric Data Register is the single consolidated record for all Bronze, Silver, and Gold datasets. It is maintained by the reach.io R package as a CSV file held in the team’s designated data store, version-controlled alongside the data. Register entries are written and updated programmatically via reach.io’s write_provenance_record() function; direct manual editing of the CSV is not permitted outside of Steward-approved corrections. In Databricks deployments, the same fields are held as a Delta table in the fw_hydrometric catalog. The Steward is responsible for keeping it current.

A separate Gauge Registry (Parquet format) is also maintained by reach.io via build_gauge_registry(). It is the routing configuration for the ingestion pipeline and records, for each gauge: source system assignment, active status, backfill completion flag, and notes. Changes to the Gauge Registry require Steward approval and are committed with a brief note describing the reason.

Rather than separate provenance, QC, and derivation records for each tier, the register uses a single table where each row is one dataset. The tier column identifies whether a row is Bronze, Silver, or Gold. Fields that only apply to certain tiers are left blank for others. This keeps everything queryable in one place and avoids the proliferation of separate files.

The register is the authoritative metadata store. Parquet files hold only the ID columns needed for joins (dataset_id, silver_dataset_id, gold_dataset_id) plus the time series data and QC columns. All other metadata lives in the register. This keeps files lean and metadata queryable without opening individual Parquet files.

17.2 10.2 Data Quality Issue Log

The Data Quality Issue Log is a separate CSV file held alongside the Hydrometric Data Register (or a second Delta table in Databricks deployments). It records known quality problems that require action beyond routine QC. Each entry includes:

  • Issue ID and date raised

  • Dataset(s) affected (Bronze and/or Silver IDs)

  • Description of the issue

  • Whether the issue originates with the supplier or with team processing

  • Action taken or planned, and by whom

  • Date resolved and how

The log is reviewed by the Steward monthly and included in the quarterly data quality summary.

17.3 10.3 Register Maintenance

The register must be updated whenever:

  • A new Bronze dataset is ingested

  • A Silver dataset is promoted, revised, or rejected

  • A Gold dataset is created, superseded, or withdrawn

  • A data quality issue is raised, progressed, or resolved

  • A supplier delivers a corrected or updated dataset

The register is version-controlled. The Delegated Steward commits changes with a note describing what was updated. Previous versions are retained as part of the retrospective traceability requirement.

18 11. Access, Sharing, and Retention

18.1 11.1 Retention

Bronze data are retained indefinitely. It is the permanent record of what was received and cannot be recreated. It must never be deleted without Owner approval.

Silver data is retained for as long as the Bronze data it was derived from is retained. Superseded Silver versions are kept alongside the current version with their status clearly labelled.

Gold data is retained for as long as any model, output, or decision that used it may need to be audited. In practice this is indefinitely for any Gold dataset that contributed to a formal flood risk output.

18.2 11.2 Access

  • Bronze: Custodians and Stewards have read access. Write access at Bronze is limited to the ingestion Custodian at the point of ingestion - after that, Bronze is read-only

  • Silver: All team members have read access. Write access (creating or revising a Silver dataset) requires Custodian role and Steward review

  • Gold: All team members have read access. Creating or superseding a Gold dataset requires Owner approval

  • External sharing of any tier requires Owner approval and must respect the supplier’s data licence

18.3 11.3 Data Licensing and Third-Party Constraints

Most hydrometric data supplied by external organisations carries restrictions on redistribution. The provenance record must note the licence or access terms under which data was received. The Steward is responsible for:

  • Checking licence terms before any external sharing of Bronze or Silver data

  • Ensuring that Gold datasets derived from restricted data carry the same restrictions

  • Flagging any licence ambiguity to the Owner before sharing

20 13. Governance and Review

This framework is reviewed annually by the Steward and approved by the Owner. The review considers:

  • Whether the Bronze to Silver to Gold tiers are serving their purpose or need adjustment

  • Data quality issue trends from the quarterly summaries

  • Any changes to supplier data formats or APIs that affect ingestion

  • Feedback from modellers and analysts on the usability of Silver and Gold data

  • Changes to the team’s operational requirements that affect what Gold products are needed

Exceptions to this framework - for example, using Bronze data directly in an urgent operational run - must be documented in the run record and reported to the Delegated Steward. Repeated exceptions in the same area should trigger a review of whether the Silver pipeline needs to be accelerated for that data source.

This framework operates under the Owner, Steward, and Custodian model in the Data & Digital Asset Governance Framework v2.0. The exceptions process, escalation paths, and annual audit requirements in that document apply here.

All dataset IDs use underscores, no spaces, no dots except as the file extension.

Tier Format and example

22 Appendix B - Glossary

Term Definition
Bronze The first tier of the medallion framework. Raw, unmodified data exactly as received from the supplier.
Silver The second tier. Quality-controlled data with flags applied and QC decisions documented.
Gold The third tier. Formally approved analysis-ready products derived from Silver data. Includes aggregated statistics, calibration inputs, and ML training sets.
Provenance The documented origin and history of a dataset - where it came from, when, how it was received, and what has been done to it.
Lineage The chain of datasets linking a Gold product back through Silver to Bronze and to the supplier.
Rating curve The relationship between water level (stage) and flow (discharge) at a gauging station, used to derive flow from level measurements.
Gap-filling Estimating values for missing time periods in a dataset using a documented method.
Quality flag A code attached to each data value indicating its quality status (Good, Estimated, Suspect, Rejected, No data, Below detection).
Flatline A sequence of identical repeated values in a time series, typically indicating a sensor or telemetry malfunction.
Medallion framework A data architecture pattern organising data into tiers of increasing quality and fitness for purpose. Adapted here for hydrological data management.
Hydrometric Relating to the measurement of water - flows, levels, rainfall, and related variables.
NRFA National River Flow Archive - the UK’s national repository of river flow data.
Datum The vertical reference level to which water level measurements are made.
Parquet A columnar file format used as the standard storage format for all hydrometric datasets in this framework. Supports typed columns, compression, and efficient partial reads.
Delta Lake A storage layer built on Parquet that adds transactions, schema enforcement, and time-travel to tables in Databricks. Used for Bronze and Silver stores in DASH.
Hydrometric Data Register A single consolidated CSV file maintained by reach.io (or a Delta table in Databricks) recording all Bronze, Silver, and Gold dataset metadata in one table. Entries are written programmatically via write_provenance_record(). Replaces separate provenance, QC, and derivation record files.
Gauge Registry A Parquet file maintained by reach.io via build_gauge_registry(). Records source system assignment, active status, backfill completion, and notes for each gauge. Acts as the routing configuration for the ingestion pipeline.
qc_value The analysis-ready value column in Silver and Gold Parquet. Equal to the Bronze value for Good data; populated with the estimated value for gap-filled rows; null for Rejected and No data rows.
Static catchment attributes Time-invariant descriptors of a catchment attached to an ML training set Gold product: area, BFI, elevation, soil type, and land cover. Repeated on every row in the Parquet file so the dataset is self-contained for model training.
BFI Base Flow Index. A measure of the proportion of river flow derived from groundwater or other slowly varying sources. Used as a static catchment attribute in ML training sets.
ML training set Gold A Gold product type holding Silver time series data at native 15-minute resolution with static catchment attributes attached. Distinct from aggregated Gold products and requires its own derivation record.
